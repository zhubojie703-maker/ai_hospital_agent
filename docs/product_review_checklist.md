# 产品评审推进清单

## 业务评审

- 目标用户是否明确：院办、运营负责人、科主任、医保办分别看什么？
- 风险评分是否能解释清楚，不只是一个黑盒分数？
- 药占比、耗材占比、平均住院日、床位使用率是否符合运营管理场景？
- 管理建议是否停留在运营复核层面，没有越界到诊疗判断？

## 数据评审

- 模拟数据是否覆盖科室、门诊、住院、收费、床位、手术和模拟病组？
- `case_drg_records` 是否能和住院记录、科室、模拟病组关联？
- 是否明确说明模拟支付标准不代表真实医保规则？
- 后续真实落地还缺哪些数据源：HIS、病案首页、医保结算清单、财务成本和绩效系统？

## 技术评审

- Text-to-SQL 是否有 SQL Guard 限制，只允许安全查询？
- RAG 回答是否能展示知识库来源和边界说明？
- 风险评分逻辑是否能独立测试和复用？
- 页面新增是否遵守现有 `PAGE_REGISTRY`、设计 token 和组件复用规则？

## 风险评审

- 页面和 README 是否避免“正式 DRG/DIP 预测”“医保结算结果”等过度表述？
- 是否明确当前版本不提供诊疗建议？
- 是否说明真实医疗和医保数据涉及隐私与机构授权？
- 是否避免用单一指标评价科室好坏？

## 面试讲述检查

- 能否用 1 分钟讲清楚项目从通用 Text-to-SQL 到医管场景的升级？
- 能否用 2 分钟讲清楚“医保控费观察”为什么是轻量版？
- 能否说明为什么不直接做正式 DRG/DIP 结算？
- 能否说明下一阶段要如何接入真实数据和评审机制？
